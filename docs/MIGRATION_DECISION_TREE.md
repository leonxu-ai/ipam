## 版本对比

### 标准版本
```python
# 仅应用层验证
migrations.AddField(
    name='scan_interval_minutes',
    field=models.IntegerField(
        default=30,
        validators=[MinValueValidator(1), MaxValueValidator(1440)],
    ),
)
```

**优点**:
- ✅ 简单直接
- ✅ 迁移速度快

**缺点**:
- ⚠️ 直接 SQL 可绕过验证
- ⚠️ 数据库脚本可插入无效值

**适用场景**:
- 仅通过 Django ORM 操作数据
- 无数据库脚本或工具
- 开发/测试环境

---

### 改进版本（v2）
```python
# 应用层 + 数据库层验证
migrations.AddField(...),
migrations.AddConstraint(
    constraint=models.CheckConstraint(
        check=models.Q(scan_interval_minutes__gte=1) &
              models.Q(scan_interval_minutes__lte=1440),
        name='networkdevice_scan_interval_valid_range',
    ),
)
```

**优点**:
- ✅ 双层数据保护
- ✅ 防止直接 SQL 绕过
- ✅ 数据完整性最高

**缺点**:
- ⚠️ 迁移稍慢（增加约束检查时间）
- ⚠️ 回滚稍复杂（需删除约束）

**适用场景**:
- 生产环境
- 有数据库脚本或ETL工具
- 严格数据完整性要求

## 我什么时候部署？

### 时间选择决策树

```
开始
  │
  └─> 业务类型？
        │
        ├─ 24/7 关键业务
        │   │
        │   └─> 寻找最低负载时段
        │        │
        │        ├─ 凌晨 2-4 点 ✅ 最佳
        │        ├─ 凌晨 1-2 点 ✅ 次选
        │        └─ 凌晨 4-5 点 ✅ 可选
        │
        ├─ 工作日业务（周一至周五）
        │   │
        │   └─> 周末部署
        │        │
        │        ├─ 周六凌晨 ✅ 最佳
        │        ├─ 周日凌晨 ✅ 次选
        │        └─ 周五深夜 ⚠️ 可选（但影响周末待命）
        │
        └─ 非关键业务
            │
            └─> 任意低峰期 ✅
```

### 部署时间建议

| 业务类型 | 推荐时间 | 备选时间 | 避免时间 |
|---------|---------|---------|---------|
| 24/7 关键业务 | 周六凌晨 2-4 点 | 周日凌晨 2-4 点 | 工作日上班时间 |
| 工作日业务 | 周六凌晨 | 周日凌晨 | 周一-周五 |
| 非关键业务 | 工作日 18:00-22:00 | 周末任意 | 业务高峰期 |

## 出现问题怎么办？

### 故障处理决策树

```
迁移失败
  │
  └─> 错误类型？
        │
        ├─ 数据库连接错误
        │   │
        │   └─> 检查数据库状态
        │        ├─ 数据库宕机 → ⚠️ 重启数据库，重新迁移
        │        └─ 连接配置错误 → ⚠️ 修复配置，重新迁移
        │
        ├─ 迁移语法错误
        │   │
        │   └─> ❌ 回滚到上一版本
        │        1. python manage.py migrate ipam 0006
        │        2. 修复迁移文件
        │        3. 重新测试
        │
        ├─ 数据验证错误
        │   │
        │   └─> 检查现有数据
        │        │
        │        ├─ 数据确实无效
        │        │   └─> 1. 回滚迁移
        │        │        2. 清理无效数据
        │        │        3. 重新迁移
        │        │
        │        └─ 验证逻辑错误
        │            └─> 1. 回滚迁移
        │                 2. 修复验证器
        │                 3. 重新测试
        │
        └─ 锁定超时
            │
            └─> ⚠️ 数据量过大
                 │
                 ├─ < 100万条
                 │   └─> 重新选择更低峰期
                 │
                 └─ > 100万条
                     └─> 使用在线迁移工具
                          - PostgreSQL: CREATE INDEX CONCURRENTLY
                          - MySQL: pt-online-schema-change
```

### 紧急回滚步骤

```bash
# Step 1: 立即回滚迁移
python manage.py migrate ipam 0006

# Step 2: 如果回滚失败，恢复数据库备份
psql ipam_db < backup_$(date +%Y%m%d)_*.sql

# Step 3: 重启应用服务
systemctl restart gunicorn
systemctl restart celery

# Step 4: 验证服务正常
curl http://localhost:8000/api/health/

# Step 5: 通知团队
# 发送告警邮件/Slack消息
```

## 监控指标

### 迁移过程中监控

```
实时监控指标:
  □ 数据库锁定状态
  □ 活跃连接数
  □ CPU 使用率
  □ 内存使用率
  │
  └─> 异常阈值
       ├─ 锁定时间 > 30秒 → ⚠️ 告警
       ├─ CPU > 80% → ⚠️ 告警
       └─ 内存 > 90% → ⚠️ 告警
```

### PostgreSQL 监控查询

```sql
-- 查看当前锁定
SELECT
    pid,
    usename,
    application_name,
    state,
    query,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- 查看迁移进度
SELECT
    schemaname,
    tablename,
    n_tup_ins,  -- 插入行数
    n_tup_upd,  -- 更新行数
    n_tup_del   -- 删除行数
FROM pg_stat_user_tables
WHERE tablename IN ('ipam_subnet', 'ipam_networkdevice', 'ipam_ipaddress');
```

## 总结：三个关键问题

### 1️⃣ 我应该部署吗？
✅ **是** - 如果：
- 在开发/测试环境
- 所有测试通过
- 生产环境有备份和回滚计划

### 2️⃣ 我应该使用哪个版本？
✅ **改进版本（v2）** - 如果：
- 生产环境
- 需要最高数据完整性
- 有直接 SQL 操作

✅ **标准版本** - 如果：
- 开发环境
- 仅通过 Django ORM 操作

### 3️⃣ 我什么时候部署？
✅ **立即** - 如果：
- 开发环境

⏰ **低峰期** - 如果：
- 生产环境
- 数据量 < 50 万

🛠️ **使用工具** - 如果：
- 数据量 > 50 万
- 无法接受锁定时间
